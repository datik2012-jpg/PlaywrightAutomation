Part 2 — HTTP methods

You should know these for the interview.

GET — retrieve something
GET /api/bookings/123

Meaning:

Give me booking 123.

Normally it shouldn't modify the booking.

POST — create/perform something
POST /api/bookings

with:

{
    "courtId": 10,
    "startTime": "18:00",
    "duration": 2
}

Could create a new booking.

Your login endpoint is also POST:

POST /api/login

Even though login isn't literally creating a database record, credentials are being submitted to perform an authentication operation.

PUT — replace/update a resource

Conceptually:

PUT /api/bookings/123

might send the complete updated representation.

PATCH — partially update

For example:

PATCH /api/bookings/123
{
    "startTime": "19:00"
}

We're changing one part.

DELETE
DELETE /api/bookings/123

Delete/cancel a resource, depending on the API design.

Don't assume every real API follows these patterns perfectly. A system might have:

POST /api/bookings/123/cancel

instead of:

DELETE /api/bookings/123

That's an API design decision.


Part 3 — Status codes you should know

Don't memorize 50 codes. For this interview, know the important ones.

Code	Meaning	QA example
200	OK	Login succeeds / GET succeeds
201	Created	Booking created
204	Success, no response body	Successful DELETE
400	Bad Request	Invalid/missing request data
401	Unauthorized	Not authenticated / invalid credentials depending on API
403	Forbidden	Authenticated but not permitted
404	Not Found	Booking ID doesn't exist
409	Conflict	Attempt to book occupied slot
422	Unprocessable Content	Structurally valid request but validation/business-data problem in APIs that use this convention
500	Internal Server Error	Unexpected server failure
503	Service Unavailable	Service temporarily unavailable

One distinction is extremely common in interviews:

401 → Who are you? You're not successfully authenticated.


403 → I know who you are, but you're not allowed to do this.

For example:

Customer isn't logged in
GET /api/admin/users


→ 401

versus:

Logged-in normal customer
GET /api/admin/users


→ 403

Day 3 — Part 5: API request structure

Now let's go deeper than status codes.

An API request can contain several important pieces:

POST /api/bookings
        ↓
URL
Method
Headers
Authentication
Body
Query parameters

For example:

POST /api/bookings
Authorization: Bearer abc123
Content-Type: application/json

Body:

{
    "facilityId": 100,
    "courtId": 5,
    "date": "2026-08-25",
    "startTime": "18:00",
    "durationHours": 2
}
Headers

Headers contain metadata about the request.

For example:

Content-Type: application/json

means we're sending JSON.

Authentication is often sent through a header:

Authorization: Bearer abc123

Here abc123 represents an access token.

Body

The body contains the data we're sending:

{
    "courtId": 5,
    "durationHours": 2
}
Path parameter

In:

GET /api/bookings/123

123 identifies a particular booking.

Conceptually:

/api/bookings/{bookingId}
               ↑
              123
Query parameters

Suppose we want bookings for a particular date:

GET /api/bookings?date=2026-08-25

Or:

GET /api/bookings?status=confirmed

These are query parameters.

Part 7.2 — Postman variables

You don't want to repeat:

http://127.0.0.1:3000

in 50 requests.

You can define a variable such as:

baseUrl = http://127.0.0.1:3000

Then requests become:

POST {{baseUrl}}/api/login
GET  {{baseUrl}}/api/bookings
POST {{baseUrl}}/api/bookings

This becomes especially useful when environments change:

LOCAL
baseUrl = http://127.0.0.1:3000


STAGING
baseUrl = https://staging.example.com


PRODUCTION
baseUrl = https://example.com

Same collection, different environment/configuration.

And we can do the same thing with authentication tokens.

Login returns:

{
    "token": "ABC123"
}

We can save it into a Postman variable and later use:

Authorization: Bearer {{token}}

So the flow becomes:

POST /api/login
      ↓
receive token
      ↓
save token
      ↓
POST /api/bookings
Authorization: Bearer {{token}}

This is a very common Postman interview topic.

Good answer. 8.5/10. You caught the two main issues: maintainability and secret handling.

A stronger interview version would be:

“Hardcoding the token in 30 requests is fragile because when the token expires or changes, every request must be updated. I would authenticate once, extract the token from the login response, save it to an environment or collection variable, and reuse it as Bearer {{token}}. For sensitive secrets, I would avoid committing them into collections or source control and use an appropriate secret store or Postman Vault where available.”

The key flow is:

POST /api/login
      ↓
receive token
      ↓
save token variable
      ↓
all other requests use {{token}}

For example, in a Postman script after login:

const body = pm.response.json();


pm.environment.set("token", body.token);

Then later:

Authorization: Bearer {{token}}

One nuance: token rotation is more of an auth/security architecture topic. For a QA interview, the more immediate point is usually automatic login → extract token → reuse token → refresh/re-login when expired.

        data={
            "email": "qa@test.com",

Then parse JSON:

body = response.json()

and validate it:

assert body["token"] != ""

If the response contains:

{
    "token": "ABC123",
    "user": {
        "email": "qa@test.com"
    }
}

we could also check:

assert body["user"]["email"] == "qa@test.com"

Notice something important:

page

is for browser/UI testing.

request

is for API requests.

So:

def test_login_ui(page):
    ...

versus:

def test_login_api(request):
    ...

No browser is required for the second test.

However, there's an important issue: with the standard Playwright pytest plugin, the fixture is commonly named api_request_context, not just request. request can also mean pytest's own request fixture, which is a completely different thing.

So for clarity, I'd teach you this version:

from playwright.sync_api import APIRequestContext




def test_login_api(api_request_context: APIRequestContext):


    response = api_request_context.post(
        "http://127.0.0.1:3000/api/login",
        data={
            "email": "qa@test.com",
            "password": "Test123"
        }
    )


    assert response.status == 200


    body = response.json()


    assert body["token"] is not None
    assert body["token"] != ""
    assert body["user"]["email"] == "qa@test.com"

One interesting QA decision

There are two ways you could validate the response.

Strict:

assert body == {
    "error": "Invalid email or password"
}

This means the entire response must be exactly this.

If tomorrow the backend adds:

{
    "error": "Invalid email or password",
    "code": "INVALID_CREDENTIALS"
}

your test fails.

Alternatively, you could check only the contract you're interested in:

assert body["error"] == "Invalid email or password"

Then adding "code" wouldn't break the test.

Neither approach is universally correct. It depends on whether the exact response schema is part of what you're testing.

Important interview question: WHERE vs HAVING

This is something you should know.

WHERE filters individual rows before grouping:

SELECT court_id, COUNT(*)
FROM bookings
WHERE status = 'confirmed'
GROUP BY court_id;

Meaning:

First take only confirmed bookings, then group them.

HAVING filters groups after GROUP BY:

SELECT court_id, COUNT(*)
FROM bookings
GROUP BY court_id
HAVING COUNT(*) > 1;

Meaning:

Group bookings by court, then keep groups with more than one booking.



Meaning:

Group bookings by court, then keep groups with more than one booking.

Easy memory:

WHERE  → rows
GROUP BY
HAVING → groups
