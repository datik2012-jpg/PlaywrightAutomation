/////////////////////////////////////Part 3 — Equivalence Partitioning /////////


Boundary vs equivalence

This is a common interview question.

Equivalence partitioning:

Divide possible inputs into groups and test representative values.

Boundary-value analysis:

Concentrate on the edges between those groups.

For duration 1–3 hours:

Equivalence:


30 min       2h        4h
  ❌          ✅         ❌
   ↑          ↑          ↑
representatives




Boundary:


<1h | 1h ---------------- 3h | >3h
      ↑                    ↑
   boundary             boundary

his sounds complicated, but it's actually simple.

Suppose the requirement says:

Booking duration must be 1–3 hours.

We could test every possible value:

0 min
10 min
20 min
30 min
...
1 hour
1.5 hours
2 hours
2.5 hours
3 hours
3.5 hours
4 hours
...

That's inefficient.

Instead, divide the inputs into groups (partitions):

        INVALID          VALID           INVALID
           ↓               ↓                ↓
    duration < 1h       1h – 3h       duration > 3h

Then choose a representative value from each group.

For example:

30 min → ❌
2 hours → ✅
4 hours → ❌

The idea is:

If 2 hours works, we usually don't need to test every possible value between 1 and 3 hours for this particular technique.

/////////////////////////////Part Severity vs Priority ////////////


This is a very common QA interview question.

Severity

How badly does the bug affect the system?

Examples:

Critical: Payment taken twice, data corruption, system unavailable.

High: Users cannot create bookings.

Medium: Booking is created but doesn't immediately appear in calendar.

Low: Button text is slightly misaligned.

Priority

How urgently should we fix it?

That's a business/release decision.

This creates an important distinction:

Severity = technical/user impact

Priority = urgency of fixing it

For example, a typo on Bond's homepage could technically have low severity, but if it's a highly visible mistake right before a major launch, Product could give it high priority.

Conversely, a serious bug in an obscure admin function used once per year might have high severity but lower immediate priority.

Recommended structure for a Codex project
my-application/
│
├── app/                    # Your application code
├── tests/                  # Automated tests
├── docs/                   # Project documents created during planning
│   ├── product-brief.md
│   ├── architecture.md
│   ├── security-plan.md
│   └── release-plan.md
│
├── agents/                 # Your team’s role definitions
│   ├── product-planner.md
│   ├── architect.md
│   ├── developer.md
│   ├── test-engineer.md
│   └── release-manager.md
│
├── ci/                     # CI/CD configuration and scripts
│   ├── test.yml
│   └── deploy.yml
│
└── README.md
Each role file is simply a clear job description. For example:
agents/product-planner.md

Role: Product Planner

Input:
- A rough product idea

Output:
- Product brief in docs/product-brief.md
- User stories
- First-version scope
- Open questions

Rules:
- Do not write application code.
- Keep the first version small.
- Ask for missing product decisions.
Then, in Codex, you say:
“Read agents/product-planner.md. Act as the Product Planner and create the product brief for my idea.”

The output is saved in docs/. The next role reads that output:
Product Planner → product brief
Architect       → architecture document
Developer       → application code
Test Engineer   → tests and quality report
Release Manager → CI/CD and release plan
These are project files that you control. Later, if a role becomes useful across many projects, you can turn it into a reusable Codex skill.
