
///////////////Day 2 — Part 1: Locators //////////////////


A locator tells Playwright which element you want to interact with.

Imagine the Bond login page contains:

<label>Email</label>
<input type="email">


<label>Password</label>
<input type="password">


<button>Log In</button>

You could write:

page.get_by_label("Email").fill("user@test.com")
page.get_by_label("Password").fill("password")
page.get_by_role("button", name="Log In").click()

This is generally preferable to something brittle like:

page.locator(
    "body > div:nth-child(2) > div > form > button"
).click()

Why?

Because the second locator depends heavily on the HTML structure. A developer adding another <div> could break your test even though the application still works perfectly.

Locator priority

Don't memorize this as an absolute rule, but a useful interview hierarchy is:

get_by_role()
      ↓
get_by_label()
      ↓
get_by_placeholder()
      ↓
get_by_text()
      ↓
get_by_test_id()
      ↓
CSS
      ↓
XPath

There's an important nuance with get_by_test_id().

For automation-heavy applications, stable test IDs can actually be excellent locators:

<button data-testid="confirm-booking">
    Book
</button>
page.get_by_test_id("confirm-booking").click()

The important idea is:

Prefer stable, user-facing or explicitly testable locators rather than selectors coupled to implementation details.

The simplest setup is to keep your app code separate from your planning docs and your role definitions. Make each role a simple text file in an agents folder describing inputs, outputs, and rules. Like, "read the idea and produce a product brief in docs." Then in Codex, ask it to read that file and act accordingly; it writes the brief into docs, and the next role reads that output.

Why get_by_role() is powerful

Suppose we have:

<button>Book</button>

We can use:

page.get_by_role("button", name="Book")

We're basically saying:

Find the thing a user/accessibility system recognizes as a button named Book.

It also encourages accessible applications.

Locator vs ElementHandle

This could appear in an interview.

A locator isn't simply a stored HTML element.

For example:

book_button = page.get_by_role("button", name="Book")


book_button.click()

Playwright resolves the locator when it performs the action.

That's useful when the DOM changes dynamically.

.first, .last, .nth()

Suppose the page contains several courts:

courts = page.get_by_test_id("court")


print(courts.count())


courts.first.click()
courts.nth(2).click()

But be careful.

If you write:

page.locator("button").nth(7).click()

that's usually fragile.

You want the locator to communicate what you're trying to interact with.

Playwright strictness

Suppose:

page.get_by_role("button", name="Book").click()

matches three buttons.

Playwright normally doesn't just randomly choose one.

You need to make the locator more specific.

For example:

court = page.get_by_test_id("court-123")


court.get_by_role("button", name="Book").click()

That's a useful interview concept.

Bond example

Imagine:

Court A
Available
18:00
[Book]


Court B
Available
18:00
[Book]

Bad:

page.get_by_role("button", name="Book").first.click()

Better conceptually:

court = page.get_by_test_id("court-A")
court.get_by_role("button", name="Book").click()

Now the test clearly communicates:

Book Court A.

Correct. C is normally the best choice. But in the interview, don't stop at “best practice”—explain why.

A stronger answer:

“I would choose get_by_role("button", name="Login") because it identifies the element by its semantic role and accessible name. It's more readable and usually more stable than XPath, CSS classes, or selectors tied to the DOM structure. If the HTML structure or CSS class changes but the user still sees the same Login button, my test can continue working.”

That's the kind of explanation they want.



Why not the others?

A — DOM structure

page.locator(
    "body > div:nth-child(2) > form > button:nth-child(4)"
)

❌ Very fragile. Adding a <div> could break the automation.

B — XPath

page.locator("//button[contains(text(),'Login')]")

It can work, but it's more implementation-oriented and usually unnecessary when Playwright provides better semantic locators.

D — CSS class

page.locator(".btn-primary")

Also works, but CSS classes often change for styling reasons and there may be many .btn-primary elements.


///////////////////////////// Part 2 — Assertions ///////////////

Locators find/interact with things.

Assertions verify that the application did what we expected.

In Playwright Python:

from playwright.sync_api import expect

Then:

expect(page).to_have_url("https://example.com/dashboard")

or:

expect(
    page.get_by_text("Booking confirmed")
).to_be_visible()

For our booking:

page.get_by_role("button", name="Book").click()


expect(
    page.get_by_text("Booking confirmed")
).to_be_visible()

The important thing is that we aren't only performing actions:

login()
select_court()
click_book()
pay()

We need to verify outcomes.

For example:

expect(success_message).to_be_visible()
expect(booking).to_be_visible()
expect(slot).to_have_text("Booked")
A common QA Automation mistake

Imagine someone writes:

page.goto("/login")
page.get_by_label("Email").fill("test@test.com")
page.get_by_label("Password").fill("123456")
page.get_by_role("button", name="Login").click()


page.get_by_role("link", name="Facilities").click()


page.get_by_text("Court A").click()


page.get_by_role("button", name="Book").click()

and says:

“My booking test passed!”

Not necessarily.

The test proved Playwright could click things without throwing an error.

It hasn't actually verified that the booking was created.

We need assertions.

Potential validations after booking:

✓ Confirmation displayed
✓ Booking status = Confirmed
✓ Correct court
✓ Correct date
✓ Correct time
✓ Correct price
✓ Booking appears in calendar
✓ Slot becomes unavailable

We don't necessarily need all of these in every test. We choose assertions based on what that particular test is supposed to prove.

Example:

def test_book_court_a(page: Page) -> None:

////////////////////////////////////Part 3 - Auto-waiting 🔥 /////////////

Imagine after clicking Book, the backend takes 2 seconds to respond.

Someone writes:

page.get_by_role("button", name="Book").click()


time.sleep(5)


expect(
    page.get_by_text("Booking confirmed")
).to_be_visible()

This is generally bad.

Why?

Answer: It is bad cause responce time can be more then 0.5 sec and test will fail , or bad when sometime passes and some time fails



Playwright's assertions can wait for the expected condition:

expect(
    page.get_by_text("Booking confirmed")
).to_be_visible()

Conceptually:

0 sec → visible? no
          ↓
        wait
          ↓
1 sec → visible? no
          ↓
        wait
          ↓
2 sec → visible? YES
          ↓
        PASS

It doesn't need to blindly sleep for five seconds.

Playwright also performs actionability checks before actions such as clicks. It checks conditions such as whether the element is visible, stable, able to receive events, and enabled as appropriate.

That's one major reason Playwright tests can be more reliable when written properly.

Important distinction

This:

time.sleep(5000)

means:

Wait regardless of what's happening.

Whereas:

expect(message).to_be_visible()

means:

Wait until the condition I actually care about becomes true, up to the configured timeout.

That's the mindset.

///////////////////////////Part 4 - Fixtures //////////////

This is one of the topics I definitely want you to understand for the Bond interview.

Imagine you have 50 tests:

def test_booking(page):
    page.goto("/login")
    # login...
def test_cancel_booking(page):
    page.goto("/login")
    # login...
def test_payment(page):
    page.goto("/login")
    # login...
def test_calendar(page):
    page.goto("/login")
    # login...

Repeating setup everywhere is bad.

Fixtures help us provide reusable test setup/resources.

If you're using Playwright with Python + pytest, you already see one:

def test_booking(page):

page is a fixture provided by the Playwright pytest integration.

You can also create your own.

For example:

import pytest




@pytest.fixture
def logged_in_page(page):
    page.goto("/login")


    page.get_by_label("Email").fill("test@test.com")
    page.get_by_label("Password").fill("password")


    page.get_by_role(
        "button",
        name="Login"
    ).click()


    return page

Then:

def test_booking(logged_in_page):
    page = logged_in_page


    page.goto("/facilities")


    # booking test

And:

def test_calendar(logged_in_page):
    page = logged_in_page


    page.goto("/calendar")


    # calendar test

Now login setup isn't copied everywhere.


Let's understand yield using only page

Suppose every test needs to open Bond.

We could create:

import pytest


@pytest.fixture
def bond_page(page):


    # SETUP
    page.goto("https://example.com")


    yield page


    # CLEANUP
    print("Test finished")

Then:

def test_facilities(bond_page):


    bond_page.get_by_text("Facilities").click()

Execution:

1. pytest creates Playwright page
              ↓
2. bond_page fixture starts
              ↓
3. page.goto(...)
              ↓
4. yield page
              ↓
         TEST RUNS
              ↓
5. test finishes
              ↓
6. fixture continues after yield
              ↓
7. print("Test finished")

So think of:

yield page

as:

“Here is the prepared page. Give it to the test. When the test finishes, come back here and continue.”

And sometimes you don't need yield

Suppose our fixture only prepares something:

@pytest.fixture
def logged_in_page(page):
    page.goto("/login")
    page.get_by_label("Email").fill("qa@test.com")
    page.get_by_label("Password").fill("123456")
    page.get_by_role("button", name="Login").click()


    return page

Then:

def test_booking(logged_in_page):
    logged_in_page.goto("/facilities")

This is fine if we don't need custom cleanup afterward.

Use yield when you need:

SETUP
 ↓
TEST
 ↓
TEARDOWN

For example:

@pytest.fixture
def logged_in_page(page):


    # SETUP
    page.goto("/login")
    # login...


    yield page


    # TEARDOWN
    # custom cleanup if needed

If they ask:

If cleanup is required, I can use yield: code before yield is setup, the yielded object is provided to the test, and code after yield performs teardown.”

def test_cancel(logged_in_page):
    print("CANCEL TEST")




def test_something_else(page):
    print("OTHER TEST")

Pytest sees that test_booking requires:

logged_in_page

So execution is:

LOGIN
↓
yield page
↓
test_booking runs
↓
test_booking finishes
↓
continue after yield
↓
CLEANUP

Then pytest moves to the next test:

LOGIN
↓
yield page
↓
test_cancel runs
↓
CLEANUP

test_something_else doesn't request logged_in_page, so that fixture doesn't run for it.

Why does pytest know which fixture to use?

Because of the function argument:

def test_booking(logged_in_page):
                 ↑
              fixture

Pytest looks for:

@pytest.fixture
def logged_in_page(...):

and executes it before the test.

So you can think of:

def test_booking(logged_in_page):

as saying:

“Before running me, please prepare logged_in_page and give it to me.”

One very important detail

By default, the fixture runs separately for each test.

So:

def test_booking(logged_in_page):

and

def test_cancel(logged_in_page):

normally means:

SETUP → test_booking → CLEANUP


SETUP → test_cancel → CLEANUP

Not:

SETUP
↓
test_booking
↓
test_cancel
↓
CLEANUP

There are fixture scopes that can change this (function, class, module, session), but don't worry about those yet.

Quick check: if I have 100 tests but only 20 contain logged_in_page as an argument, how many tests will use that fixture?



Fixture is one improvement

Instead of 200 copies:

@pytest.fixture
def logged_in_page(page):
    page.goto("/login")
    page.get_by_label("Email").fill("qa@test.com")
    page.get_by_label("Password").fill("password")
    page.get_by_role("button", name="Login").click()


    return page

Then:

def test_booking(logged_in_page):
    page = logged_in_page

Better: Playwright authentication state

Playwright can save authenticated browser state—such as cookies and local storage—and reuse it.

Conceptually:

LOGIN ONCE
    ↓
save authenticated state
    ↓
auth.json
    ↓
┌──────────┬──────────┬──────────┐
Test 1     Test 2     Test 3
already    already    already
logged in  logged in  logged in

For example, during setup:

page.goto("/login")
page.get_by_label("Email").fill("qa@test.com")
page.get_by_label("Password").fill("password")
page.get_by_role("button", name="Login").click()


page.context.storage_state(path="auth.json")

Now we've stored authentication state.

Later, a browser context can be created using that state:

context = browser.new_context(
    storage_state="auth.json"
)

Tests can start already authenticated.

Important interview distinction

Fixture:

Helps organize reusable setup/cleanup.

Storage state:

Allows Playwright to reuse authentication state instead of repeatedly logging in through the UI.

They solve related but different problems.


Quick interview question

Bond has:

10 tests specifically testing login
190 tests testing booking, payments, calendar, membership, etc.

Would you use saved authentication state for all 200 tests, or only some of them?

And why?

Answer: I consider for example we pick up login (one from ten) and saved it and run booking,payments,calendar,membership etc. Then we use different Login option and as well save it and use for tests.

Yes — that’s the right idea. I’d refine it a bit for interview wording.

You generally would not use saved auth state for the 10 login tests, because those tests are specifically verifying the login flow itself. They should actually enter credentials and validate successful/failed login behavior.

For the other 190 tests, using saved authentication state is a good approach because login is just test setup, not the feature under test.

Your idea about multiple login types is also strong. For example, if Bond has different roles, you could save separate auth states:

admin_auth.json
customer_auth.json
staff_auth.json

Then:

Booking tests → customer auth
Admin tests → admin auth
Staff tests → staff auth

That avoids repeating UI login while still letting you test permissions correctly.

A strong interview answer would be:

“I would keep the login tests independent and perform real login there. For booking, payment, calendar, and membership tests, I would reuse saved authentication state because authentication is only a prerequisite. If the system has multiple roles, I would maintain separate saved states for each role.”

That’s a very good Playwright design answer.

This is also perfectly valid POM:

class BookingPage:
    def __init__(self, page):
        self.page = page


    def book_button(self):
        return self.page.get_by_role("button", name="Book")


    def court(self, name):
        return self.page.get_by_text(name)


    def book(self):
        self.book_button().click()


    def select_court(self, name):

Example (but POM is less valid then i have mention before):


Bond example

We could create:

class BookingPage:


    def __init__(self, page):
        self.page = page
        self.book_button = page.get_by_role(
            "button",
            name="Book"
        )


    def select_court(self, court_name):
        self.page.get_by_text(court_name).click()


    def select_time(self, time):
        self.page.get_by_text(time).click()


    def book(self):
        self.book_button.click()

Our test becomes:

def test_book_court(page):


    booking = BookingPage(page)


    page.goto("/facilities")


    booking.select_court("Court A")
    booking.select_time("18:00")
    booking.book()


    expect(
        page.get_by_text("Booking confirmed")
    ).to_be_visible()

The test now reads almost like English:

Open facilities
Select Court A
Select 18:00
Book
Verify confirmation
Why POM helps

Imagine the developer changes:

<button>Book</button>

to:

<button>Confirm Booking</button>

Without POM, perhaps 40 tests contain:

page.get_by_role("button", name="Book")

We might need to update many tests.

With POM, we change:

self.book_button = page.get_by_role(
    "button",
    name="Confirm Booking"
)

in one place.

That's the major maintenance advantage.

But don't make a giant Page Object

Bad architecture:

BondPage
 ├ login()
 ├ logout()
 ├ book()
 ├ cancel()
 ├ pay()
 ├ refund()
 ├ register()
 ├ create_member()
 ├ delete_member()
 ├ generate_report()
 ├ ...

Eventually you have a 5,000-line monster.

Prefer logical pages/components:

LoginPage
BookingPage
CalendarPage
PaymentPage
MembershipPage

Potentially components too:

CalendarComponent
NavigationComponent
PaymentModal


//////////////Day 2 — Part 6: API testing with Playwright /////////////////////


Now we connect UI automation with APIs.

Playwright isn't only for browser testing. It can also send HTTP requests.

Conceptually:

response = request.get(
    "https://api.example.com/bookings/123"
)

Then:

expect(response).to_be_ok()

and:

data = response.json()


assert data["status"] == "confirmed"

Why is this useful?

Imagine we're testing:

Cancel booking

We could prepare everything through UI:

Login
↓
Find facility
↓
Select court
↓
Select time
↓
Book
↓
Pay
↓
Open calendar
↓
Find booking
↓


NOW finally test cancellation

That's slow and creates many possible failure points.

Instead, depending on the available API:

API → create prerequisite booking
          ↓
UI → open booking
          ↓
UI → CANCEL
          ↓
UI/API → verify cancellation

Now our test is focused on cancellation.

This connects to the api_client example that confused you earlier. We could eventually build our own API helper, but first understand the concept.

Another useful pattern

UI performs action:

UI
↓
Book Court A

Then API verifies backend state:

GET /bookings/123
↓
{
    "court": "Court A",
    "status": "confirmed"
}

This can give us stronger validation than checking only a success message.
